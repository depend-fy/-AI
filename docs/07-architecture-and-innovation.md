# 智鉴 AI · 技术架构与核心创新点

## 一、一页式简介

| 项目 | 内容 |
| --- | --- |
| 名称 | 智鉴 AI（VeriMind AI） |
| 定位 | 多模型协同的 AI 幻觉检测、证据溯源、错误归因与自动修正系统 |
| 要解决的问题 | 大模型输出可能存在虚构文献、引用与结论不匹配、数值/时间错误、推断过度、证据不足、来源冲突——而**同一个模型很难可靠地识别自己的错误** |
| 核心思路 | 把"检测幻觉"拆成 **11 个职责单一、可单独测试的环节**；大模型只产出结构化判断，**最终结论由可解释的规则表裁决**；修正必须过**独立复核**才允许进正文 |
| 关键数字（实测） | 主张级**误报率 0%**；完整流程在 100 条标注集上精确率 97.6% / 召回率 78.4% / F1 87.0%；单条检测 2–3 次模型调用；重复检测 0 费用（命中缓存） |

**为什么这样分层**：业务层是**纯函数 + Pydantic 出入参**，界面只负责展示与传 `run_id`。
好处是：可以用 pytest 直接测业务（234 个测试全部离线可跑）；将来要包 FastAPI 或多端复用，业务代码一行不用改。

## 三、数据流（11 步，每步都有明确输入输出）

| 步 | 环节 | 输入 → 输出 | 用什么 |
| --- | --- | --- | --- |
| ① | 校验输入 | 原文 → 合法文本 | 代码 |
| ② | 规则引擎拆解（**基线，永远执行**） | 文本 → 主张（含精确字符位置） | 正则 + 关键词 |
| ③ | 大模型拆解 | 文本 → 主张草稿（只给引用原文） | 主模型 |
| ④ | 文内一致性检查 | 主张 → 矛盾（同 DOI 两年份 / 同指标两数值） | 代码 |
| ⑤ | 外部证据检索 | 主张 → 证据 + 检索痕迹 + 原始响应留档 | Crossref / OpenAlex / arXiv |
| ⑥ | 元数据匹配 | 证据 → 存在性/书目信息的支持或反驳 | 确定性规则 |
| ⑦ | 证据审查员（角色 B） | 摘要 + 主张 → 内容层面的关系（**必须引用原句**） | 主模型 |
| ⑧ | 规则裁决 | 证据 + 信号 → 6 状态 + 8 问题类型 + 缺失证据 | **规则表（不是模型）** |
| ⑨ | 事实审查员（角色 A） | 主张 → 怀疑方向（写入角色意见） | 主模型 |
| ⑩ | 修正员（角色 C） | 有问题的主张 + 证据 → 最小改动建议 | 主模型 |
| ⑪ | 独立复核员（角色 D） | 修正 + 证据 → 3 项确定性检查 + 2 项语义检查 | **代码 + 另一个厂商的模型** |

## 四、五个核心创新点

### 创新点 1：把"判断层面"变成类型级约束（本项目最关键的设计）

"文献是真的"和"文献真的这么说"是两个问题。系统用 `JudgedAspect` 把判断显式分层：

| 层面 | 允许用什么判断 | 由谁判断 |
| --- | --- | --- |
| 文献是否存在 | 注册机构记录（查到 / 明确 404） | 确定性规则 |
| 书目信息（年份/期刊） | 权威元数据逐项比对 | 确定性规则 |
| **内容结论是否被支持** | **必须有摘要/全文** | 角色 B，且**必须引用摘要原句** |

这条约束**由 Pydantic 校验器强制**：用"仅元数据"的证据去判断内容层面，程序直接抛错。
不是靠提示词请求模型自觉——**代码层面就不可能越界**。

### 创新点 2：模型不下最终结论，规则表负责裁决

大模型只输出可观察的信号与怀疑方向；6 种状态、8 类问题、严重度由
`verification/rules.py` 的**规则表**（`I1–I4 / U1 / E1–E7 / N0–N6`）决定。
于是每条结论都能回答"**命中了哪条规则、为什么**"，而且规则是纯函数、可穷举测试、改一条立刻能回归。

### 创新点 3：确定性护栏把"看起来对的错误"拦下来

修正环节最容易"改出新错误"，所以复核有五项检查，其中**三项由代码完成**（模型无法推翻）：

1. 写入新事实的修改是否引用了证据；
2. 修正后新出现的年份/数值/DOI 能否在**所引证据**里找到；
3. 是否引入了原文与**全部证据**里都没有的内容（凭空编造）。

模型说"通过"不算数——代码否决就是否决。

### 创新点 4：无证据不判错 + 区分"不存在"与"查不到"

- 「证据不足」「暂无法核验」是一等公民状态；**绝不**把"查不到"说成"错误"；
- 注册机构**明确 404** 才允许判"引用不存在"；**网络失败**只能说"暂无法核验"（规则 `N0`）；
- 检索到论文但拿不到摘要 → 规则 `N6`「证据不足」，**不因为查到论文就默认它支持原文**。

### 创新点 5：真正的跨厂商独立复核 + 如实标注模式

修正员与复核员用**不同厂商的模型**（deepseek-chat / agnes-3.0-flash），
"改的人"和"检查改得对不对的人"分离；未配置独立复核员时，
界面与报告会明确写「复核独立性有限」，**不假装独立**。

## 五、角色分工与可解释性

| 角色 | 职责 | 模型 |
| --- | --- | --- |
| 主张拆解员 | 文本 → 原子主张（只负责引用原文，位置由代码算） | 主模型 |
| 事实审查员（A） | 这条主张要核验什么、最可能哪里出错 | 主模型 |
| 证据审查员（B） | 证据在**内容层面**支持/反驳/无关（必须引用原句） | 主模型 |
| 修正员（C） | 最小改动建议（改事实必须有证据） | 主模型 |
| 独立复核员（D） | 从怀疑立场复核修正 | **另一家模型** |
| 规则裁决层 | 6 状态 / 8 问题类型 / 严重度 / 缺失证据 | **代码** |

**报告里能追问到底**：原文位置（字符级高亮）→ 判断理由 → 命中的规则编号与说明 → 证据（可点击链接 + 原始响应留档路径）→
角色分歧 → 修正前后 → 五项复核检查 → 未解决问题 → 系统局限。
